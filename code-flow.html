结论

每个算法目录都是一条独立竖切，目录之间不互相 import；experiments/ 是唯一的横切层，用子进程按同一协议调用 5 个算法。

  1. 全仓库 109 个 .py、185 个 def / class，没有跨目录 import。
  2. 算法差异收在 agents.py，训练循环统一在 trainer.py。
  3. experiments/ 用 sys.path 加子进程复用算法目录，不修改它们。
  4. 评估协议写在驱动层：固定 seed、固定 20 个评估起始状态。

适用于仓库 fbe0e5f2026-10-27统计不含 .venv、__pycache__、legacy_v1

一条算法目录由哪几层组成？

上图每一格都是一个 .py 文件，后五格是纯函数或纯模块，只有 main.py 负责把它们连起来。networks.py 不在这条链上：它只提供网络类，由 agents.py import。trainer.py 只拿到一个 agent 对象，看不到网络和优化器。

训练时谁在什么时候更新？

更新频率是三条分支间最大的代码差异：off-policy 每步更新，on-policy 攒批更新。

类别谁调用更新频率一次用多少数据
off-policy（09–11）trainer.py 内循环每个 env step从 replay buffer 采一个 batch
on-policy CartPole（07、08）trainer.py 外层每回合一次200–500 步的整条轨迹
on-policy Pendulum v2（07、08）trainer.py 外层每 10 回合一次2000 步，切成 64 的 minibatch

off-policy 的更新藏在 step 循环里，done 只控制回合何时结束：DDPG 训练循环2。on-policy 的 v2 改成先攒 10 个回合再调一次 agent.update：成批采集3

dones 只记 terminated，ends 记回合边界。Pendulum 永远不会 terminated，所以 200 步的截断处仍要用 V(s') 做 bootstrap。

experiments 如何横切各算法？

experiments/ 不 import 算法代码，而是拼一条命令行交给子进程；子进程再用 sys.path 把算法目录顶到搜索路径最前面。命令构造4 驱动层导入5

图的结构
  • run_all → run_one* driver
  • 算法目录 algos
  • raw/*.json raw
  • analyze analyze
  • driver → algos · 子进程 + 导入 agents
  • driver → raw · 写 JSON
  • raw → analyze · 读全部 seed

run_all 负责调度：50 次运行由 ThreadPoolExecutor 并发，已有 JSON 自动跳过，失败会写 results/logs/；每个子进程跑一个 run_one 或 run_one_onpolicy。分析脚本只读 raw/，五个算法的顺序写在 ALGOS 里，最后输出三张图和 tables.md。算法清单6

评估起始状态
EVAL_SEED=10000 起的 20 个，所有算法共用
评估频率
off-policy 每 2k 步，on-policy 每 10k 步
确定性动作
DDPG、TD3 用 actor(s)；SAC 用 tanh(mu)；PPO、TRPO 用 mu
