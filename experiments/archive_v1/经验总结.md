# 强化学习对比实验经验总结

本文件汇总 `experiments/` 下所有对比实验（图 1 / 图 2 / gamma 诊断）的结果、
结论和训练性能优化建议。三个算法目录里的 `经验总结.md` 保持上游原文，不再各自
追加实验内容。

## 0. 实验范围与协议

| 项 | 图 1（off-policy） | 图 2（on-policy） |
|---|---|---|
| 算法 | DDPG / TD3 / SAC | PPO / TRPO（SAC 作 40k 参照） |
| 环境 | Pendulum-v1 | Pendulum-v1 |
| seeds | 0 / 1 / 2 | 0 / 1 / 2 |
| 训练预算 | 200 回合 × 200 步 = 40k | 2000 回合 × 200 步 = 400k |
| gamma | 各算法原配置（DDPG 0.98，TD3/SAC 0.99） | 统一 0.99（文档要求 PPO 从 0.9 改 0.99；TRPO 同） |
| periodic eval | 每 5k 步，5 回合 | 每 10k 步，5 回合 |
| 最终评估 | 20 回合确定性策略，`EVAL_SEED=10000` | 同左，PPO/TRPO 用 `mu` |
| 训练曲线 | 滑动平均窗口 10；细线=单 seed，粗线=中位数 | 同左 |

评估口径：训练回报含探索噪声，**只用于画曲线，不用于算法间比较**；性能数字
只取训练结束后的确定性评估。所有算法共用同一组 eval seed（10000–10019），
避免“运气好/坏”混入算法差异。

## 1. 结果总表

### 1.1 图 1：DDPG / TD3 / SAC（40k 步，3 seeds）

| 算法 | 最终评估（中位数 [Q1, Q3]） | IQR | steps-to-90% | 耗时中位数 |
|---|---:|---:|---:|---:|
| DDPG | -150.9 [-347.8, -139.0] | 208.8 | 10k | 160 s |
| TD3 | -122.8 [-123.4, -122.7] | 0.7 | 10k | 212 s |
| SAC | **-120.6** [-121.2, -120.4] | 0.9 | **5k** | 487 s |

- DDPG 的 seed 0 最终只有 -544.6，seed 1/2 是 -127.0/-150.9；IQR 208.8，方差
  明显最大，图 1 中浅蓝细线在 20k 附近可见掉坑。
- TD3 与 SAC 的最终性能几乎打平（-122.8 vs -120.6），但 SAC 的墙钟耗时是
  TD3 的 2.3 倍。
- 因此在这个任务上：**SAC 样本效率最高，TD3 墙钟性价比最好，DDPG 最不稳定**。

### 1.2 图 2：PPO / TRPO（400k 步，gamma=0.99，3 seeds）

| 算法 | 最终评估（中位数 [Q1, Q3]） | IQR | steps-to-90% | 耗时中位数 |
|---|---:|---:|---:|---:|
| PPO | -593.5 [-728.2, -581.6] | 146.7 | 245k | 420 s |
| TRPO | -1403.4 [-1440.3, -1022.2] | 418.0 | 390k | 349 s |
| SAC（40k 对照） | -120.6 | 0.9 | 5k | 487 s |

- 样本效率差一个数量级成立：SAC 5–10k 步就到 -150 左右，PPO/TRPO 跑到 400k
  仍未达到。
- 但 **PPO/TRPO 的绝对水平远低于文档预期**，没有复现“SAC 20k ≈ PPO 400k”。

### 1.3 gamma 诊断（PPO / TRPO）

| 配置 | 最终评估 | train last-10 |
|---|---:|---:|
| PPO γ=0.99（seed 0） | -569.7 | -645.6 |
| PPO γ=0.9（seed 0） | **-338.2** | **-214.6** |
| 仓库原始记录 PPO γ=0.9 | -338.146 | — |
| TRPO γ=0.99（seeds 0/1/2） | -641 / -1403 / -1477 | — |
| TRPO γ=0.9（seed 0） | -880.6 | -867.1 |
| 仓库原始记录 TRPO γ=0.9 | -289.503 | — |

结论：

1. **驱动层正确**：PPO γ=0.9、seed 0 得到 -338.2，和仓库记录 -338.146 几乎
   完全一致；差异来自评估协议（我们用 20 回合确定性 `mu`）。
2. **单独改 gamma 会让 PPO 变差**：同一 seed 下 -569.7 vs -338.2。其余超参
   （`CRITIC_LR=5e-3`、`REWARD_SCALE=8`、`EPOCHS=10`、`ACTOR_LR=1e-4`）是按
   γ=0.9 调的；γ 变大后 value target 量级约放大 10 倍，critic/advantage 的
   尺度不再匹配。
3. **TRPO 对 seed 极敏感**：0.99 的三个 seed 差到 800 分；0.9 的 seed 0 也只有
   -880.6，仓库的 -289.5 没有复现。TRPO 只能作为“可选/诊断”，不能据此下强结论。
4. 文档的“SAC 20k ≈ PPO 400k”在当前实现/超参下不成立；如果要把 PPO 用在
   面试或文档里，需要先重新调参，而不是只改 gamma。

### 1.4 吞吐参考（含 periodic eval，量级参考）

| 算法 | 预算 | 耗时中位数 | 约 steps/s |
|---|---:|---:|---:|
| DDPG | 40k | 160 s | ~250 |
| TD3 | 40k | 212 s | ~189 |
| SAC | 40k | 487 s | ~82 |
| PPO | 400k | 420 s | ~952 |
| TRPO | 400k | 349 s | ~1146 |

on-policy 每步便宜得多（每次 episode 才更新一次），但需要多一个数量级的步数；
off-policy 每步贵，但样本效率高。这两条曲线不能只比 wall-clock 或只比 steps。

## 2. 训练性能与算子优化

以下内容原先分散写在三个算法目录里，现统一迁移到这里。行号对应各算法目录
当前的 `agents.py`（实验驱动没有改动这些文件）。

### 2.1 共同瓶颈：不是算力，是启动和同步

网络是 `3→64/128→…→1`、batch 64/100，单个 update 的 FLOPs 极低。实测
GPU 利用率约 12%、进程专用显存约 180 MB（任务管理器显示的 2 GB 是整卡总占用，
包含桌面/浏览器等）。这种规模下，瓶颈是每步几十个 tiny kernel 的启动，以及
`GPU→CPU` 同步；手写 CUDA 算子不会有明显收益。

### 2.2 DDPG

1. **缓存动作边界**：`take_action()` 每个 env step 调两次 `.cpu().numpy()`
   取 `action_bias/action_scale`（`09_DDPG/Pendulum/agents.py:51-52`），
   40k 步就是 80k 次同步。在 `__init__` 里存成 CPU ndarray 即可。
2. **软更新批量化**：`soft_update()` 逐参数 `mul_` + `add_`
   （`agents.py:54-60`）。改用 `torch._foreach_mul_` / `torch._foreach_add_`，
   把两个网络的所有参数合并成批量 kernel，数值等价。
3. **fused Adam**：优化器构造加 `fused=True`（`agents.py:25-26`）。PyTorch 2.11
   在 CUDA 上提供 fused Adam；数值可能有极小差异，需要 benchmark。
4. 可选：`torch.compile(agent.update, mode="reduce-overhead")`；或把 replay
   buffer 放到 GPU。batch 64 时收益有限，改动较大。

### 2.3 TD3

1. **删掉热路径 `.item()`**（收益最大、零风险）：
   - `actor_loss.item()`：`10_TD3/Pendulum/agents.py:196`，每 2 步一次；
   - `critic_loss.item()`：`agents.py:211`，每步一次。
   40k 次 update + 20k 次 actor 更新，约 60k 次 GPU→CPU 同步；而训练循环
   根本不使用返回的字典。去掉 `.item()` 或加 `return_losses=False` 开关。
2. **软更新批量化**：`agents.py:96-103`，同样改 foreach。
3. **fused Adam**：三个优化器构造处 `agents.py:40-47`。
4. **冻结 critic 的 Python 开销**：actor 更新时逐个参数
   `requires_grad_(False/True)`（`agents.py:183-202`）。更干净的做法是用
   `torch.autograd.grad(actor_loss, self.actor.parameters())` 只对 actor 求梯度；
   收益小于前两项。
5. 可选：`torch.compile(update, mode="reduce-overhead")`；先去 `.item()`，
   否则容易 graph break。

### 2.4 SAC

1. **软更新批量化**：`11_SAC/Pendulum/agents.py:72-78`，两个 target critic
   每步各一次；改 foreach。
2. **fused Adam**：四个优化器构造处 `agents.py:30-39`。SAC 每步优化器调用最多，
   收益可能比 TD3/DDPG 更明显。
3. **`torch.compile(update, mode="reduce-overhead")`**：SAC 的 `update()` 是
   静态计算图（没有 `.item()`、没有数据依赖分支），最适合编译；tiny-batch 下
   常见 1.5–3×。需要确认 `log_alpha` 的 `requires_grad` 参数能被正确处理。
4. **评估路径**：训练时从高斯策略采样；评估必须用 `tanh(mu)`
   （`run_one.py` 的 `deterministic_action` 就是这么做的），不要用 `rsample()`。
5. **墙钟与样本效率的权衡**：Pendulum 上 SAC 最终只比 TD3 好 2 分，但慢 2.3 倍；
   SAC 的优势要在样本昂贵（真机）或更难的任务上才明显。

### 2.5 PPO / TRPO（on-policy）

- 每个 episode 才更新一次，优化器调用次数远少于 off-policy；PPO 400k 步
  420 s，吞吐已经很高。当前主要问题不是 kernel 启动，而是**样本效率**和
  **超参与 gamma 不匹配**。
- 先把 PPO 的 gamma/超参调好（例如 `CRITIC_LR` 降到 1e-3 左右、
  `REWARD_SCALE` 重新标定），再谈算子优化；否则优化的是错误的瓶颈。
- TRPO 的 HVP/CG 本身开销较大，不建议在 Pendulum 上继续做微优化；换到
  MuJoCo 后再评估。

### 2.6 实验纪律

- 数值等价、可以只提速：缓存动作边界、去 `.item()`、foreach 软更新。
- 不保证逐位一致：fused Adam、`torch.compile`。**若报告 wall-clock，所有
  seed 必须用同一版代码重跑，不能新旧混报。**
- 不要为了“提高 GPU 利用率”增大 batch、降低更新频率或改用并行环境：
  那会改变算法/样本效率，训练曲线不再可比。
- 上 MuJoCo 1M 步后，再考虑 vectorized env + 更大 batch + compile，收益
  比 Pendulum 明显得多。

## 5. 局限与下一步

- **n=3**：只能报中位数/IQR，做不了 IQM/bootstrap 置信区间，也不应做显著性
  检验。不要用这组结果宣称“某算法显著更好”。
- Pendulum 是教学环境，不是公认 benchmark；这套实验的价值是跑通评估协议、
  暴露实现问题，为后续 MuJoCo / Meta-World 复用。
- PPO/TRPO 当前结果不能代表算法本身的上限；下一步应先做小范围超参搜索
  （gamma=0.99 下的 `CRITIC_LR`、`REWARD_SCALE`、`ACTOR_LR`），再跑 3 seeds。
- 若后续要做鲁棒性/扰动实验，`results*/models/` 里的 actor 权重可以直接复用，
  不必重训。
